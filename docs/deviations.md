## Two runs at once on Kaggle's T4 x2 (2026-11-26)
- Kaggle's T4 session has two GPUs. Runs go in pairs (`scripts/run_pair.py`), each on its own GPU via CUDA_VISIBLE_DEVICES, sharing one copy of the cache in the OS page cache (two private copies would not fit in RAM). The step count S is measured with two runs going at once (M3+M4 rerun). Seeds, configs and the eval protocol are unchanged.
- Fixes after the first M3+M4 run: the cache was never read into RAM (`np.ascontiguousarray` returns the memmap without copying), so early steps read from disk and the measured s/step (and S) was wrong; the cache is now read once sequentially (page cache) before training. The real-data overfit check now uses the training's mixed-precision mechanics (fp16 autocast + GradScaler + grad clipping); thresholds unchanged.
- Random-data unit tests (`tests/test_expert.py`, approved 2026-11-26): the fixed L1 thresholds (regression < 0.02 after 1000 steps, flow < 0.05 after 3000 steps) are replaced by a relative check: the training loss (mean of the last 100 steps) must be at most 10 % of the first step's loss. Reason: the fixed values were guesses, missed narrowly in fp32 (0.0210, 0.082), and do not detect bugs better than a relative drop. Real-data overfit checks keep their approved thresholds. Launching A_s0 and C_s0 was approved on the condition that only these two tests fail in the M3+M4 rerun, their 3x-step versions pass, and every real-data check passes.
- After the second M3+M4 run (approved 2026-11-26): (a) each paired run picks its GPU with `torch.cuda.set_device` (env MINIVLA_GPU) instead of CUDA_VISIBLE_DEVICES, which made robosuite's EGL renderer request a device that was not visible; MuJoCo renders on GPU 0 for both runs. (b) The real-data overfit checks keep their thresholds (C L1 < 0.02, A L1 < 0.05) but now use the training's LR schedule shape (warm-up 1000 steps, cosine decay to the same final/peak ratio, peak lr 1e-3) and more steps (C 3000, A 10000); the loss curve is logged. Evidence for the change: with fixed noise and time the flow loss reached 0.0005 (the model can fit), and fp32 was no better than fp16 + GradScaler, so precision was not the cause. (c) New CPU-only toy test (`scripts/flow_toy.py`): the flow head must learn a bimodal 2-D distribution with the eval's sampler and time convention; it runs before any further GPU run. (d) S = 19,047 for all six models (rule: min(20000, ⌊3600 / 0.189⌋), slowest head A at 0.189 s/step with both runs at once, second M3+M4 run).

## Project 2: DINO-WM on Wall (approved 2026-11-27, docs/p2_spec.md)
- Environment: official repo at `0a9492f` in a uv Python 3.9.19 venv with torch 2.3.0 (cu121); all installs constrained by environment.yaml's pip pins; only the packages the Wall code path imports (list: `results/p2_requirements.txt`). MuJoCo 2.1 + mujoco-py 2.1.2.14 are installed (README recipe) only because plan.py imports env/__init__, which imports PointMaze; mujoco-py is built CPU-only (MUJOCO_PY_FORCE_CPU=1); Wall never uses MuJoCo. wandb runs with WANDB_MODE=disabled.
- Data: wall_single.zip expands to 59 GB (> Kaggle's 20 GB output disk), so it is extracted to /tmp in every run.
- Training settings come from the official Wall checkpoint's saved `hydra.yaml` where it has the key, else from the repo's `train.yaml` (approved rule). Overrides vs the repo: `num_hist=1` (repo 3), `training.batch_size=128` (repo 32), `predictor.emb_dropout=0.1` (repo 0), `~decoder.channel` (the checkpoint config has no channel key, so the VQVAE class default 128 applies; the repo's yaml sets 384), `frameskip=5` (same). Hardware: `env.num_workers=4` (Kaggle CPUs; the checkpoint used 0 with 32 processes of batch 4). Not taken from the checkpoint: `training.epochs` (checkpoint config 1000, but the saved model is from epoch 65; paper 100; ours = reduced budget E), `debug` (only changes the wandb project name), `ckpt_base_path`.
- The official checkpoint is `model_latest.pth` from epoch 65; it was trained with an effective batch of 128 over 32 processes (gpu_batch_size 4).
- Success (from code, `env/wall/wall_env_wrapper.py:61`): `||goal[:2] - cur[:2]|| < 4.5`.
- DINOv2 encoder code: the official `models/dino.py` loads `torch.hub.load("facebookresearch/dinov2", ...)` unpinned (today's main, which needs Python >= 3.10 and fails on the official 3.9). We place dinov2 at `e1277af` (main as of 2024-09-12, the official Wall checkpoint's training date) in torch.hub's cache folder, which torch.hub then uses; the official code is unchanged. The pretrained ViT-S/14 weights file is the same.
- Speed-up ruled out: the stored pixels are float32 in 0-255 but not integer-valued, so a uint8 copy of the data would not be lossless.
- Planning the official checkpoint without its decoder (approved 2026-11-27): on the T4 (16 GB) the official planner ran out of memory in the VQ-VAE decoder (P2-R1 v3). Checked in the code first: `planning/evaluator.py` `eval_actions` computes success in `_compute_rollout_metrics` via `self.env.eval_state(self.state_g, e_state)` on the simulator's final states, before and independently of the decoder, which is only used afterwards `if self.wm.decoder is not None` to plot predicted vs. real frames. We plan with a copy of the checkpoint folder whose `hydra.yaml` says `has_decoder: false` (plan.py `load_model` then sets the decoder to None); the checkpoint file, plan_wall.yaml (MPC-CEM, 50 evals, seed 99) and the success rule are unchanged. Lost: the comparison plots/videos.
- Our training is without the decoder (`has_decoder=False`): the approved 15 % rule could not be applied because decoder-on training does not fit a T4 at batch 128 (P2-R1 v3); the decoder is not used for success, as above.
- Frame-level reader (approved 2026-11-27, option b with a 30-minute test and a 2x rule): the official loader `torch.load`s a whole 30.7 MB episode file and transforms all 50 frames for every 2-frame training sample. `scripts/p2_fastdata.py` stacks the episode files once into `obses.npy` (float32, the same values) and `scripts/p2_fastdata.patch` makes the official loader read and transform only the frames a sample uses (Resize/CenterCrop/Normalize work frame by frame). Used only if 64/64 training samples are exactly equal to the official reader's and the decoder-off s/step is >= 2x faster than P2-R1's (8.39 s/step); otherwise the official reader is used and E = floor(180 / 77.5) = 2 (option a). Data path only: model, losses, optimiser and batch order unchanged.
- Reduced budget: E = floor(180 min / measured min per epoch), capped at 100 (paper: 100; the official checkpoint is from epoch 65). `training.save_every_x_epoch` stays at the repo default 1 (checkpoint config: 5), so the final epoch is always saved; `plan_settings.plan_cfg_path` stays at the repo default null (no planning jobs during training). Planning uses the final checkpoint only.
- Two jobs in one session: our training on GPU 0 while the official checkpoint is planned on GPU 1 (CUDA_VISIBLE_DEVICES; safe here because MuJoCo is CPU-only); our own planning runs after training.
- Frame-level reader test result (P2-R2 v1): the one-time conversion did not finish within its 20-minute limit and /tmp then became read-only, so no speed-up was shown within the approved 30 minutes; per the approved rule our training uses the official reader (option a): E = floor(180 / 77.5) = 2 epochs, reduced budget.
- Project 2 scope (approved 2026-11-27, option c): our own training is dropped (P2-R2 v2: one epoch takes ~2.5 h on a T4 incl. validation, and the official validation loop runs out of memory at batch 128). P2 is a **reproduction of evaluation and planning with the official checkpoint; training not reproduced**: MPC-CEM (plan_wall.yaml unchanged; paper Table 1: 0.96) vs. plain CEM (the repo's conf/planner/cem.yaml values, opt_steps 30, written as overrides of plan_wall.yaml's planner block; paper Table 8: 0.74), 50 start/goal pairs each, seed 99, Wilson 95 % CIs.
- wandb: plan.py's main() hard-codes `wandb_logging = True`, so it cannot be turned off by an override; we set WANDB_DISABLE_SERVICE=true (with WANDB_MODE=disabled) so wandb.init starts no background service (it failed to start in P2-R2 v2). Logging only; no code change.
- Planning output folders: `hydra.run.dir=plan_outputs/<tag>` (location only), so the two planners can run at once, one per GPU.
- MPC-CEM stopped by our time limit (P2-R3 v1, reported as decided 2026-11-28). plan_wall.yaml has `max_iter: null`, so the official MPC loop only stops once all 50 pairs succeed. On a T4 one MPC iteration takes about 75 min, and our 300-min limit stopped the run after 4 iterations. We report the official code's own cumulative count at that point: a pair counts as a success if it reached the goal at any iteration so far (`mpc.py` `is_success |= successes`; the evaluator judges each pair at its first-success step via `action_len`). The result is **46/50 (92%, CI 81.2–96.8) after 4 MPC iterations, stopped by our time limit; the paper reports 0.96; the intervals are consistent.** The paper (arXiv 2411.04983v2, Table 1, Table 8, Appendix A.5.1(f)) says only that MPC runs "until success is achieved or after a fixed number of iterations that we set as hyperparameter". It gives no value, and no step or time limit, so our stopping point cannot be matched to theirs. Numbers come from the run's log and logs.json; nothing was rerun (results/p2_r3.md).
- Plain CEM (P2-R3 v1) did not run: our override `~planner.max_iter` fails because Hydra will not delete a key whose value is null. The official sweep code (`plan.py` `build_plan_cfg_dicts`) instead merges `planner/cem.yaml` onto the plan config's planner block, and CEMPlanner ignores the leftover keys through `**kwargs`. Fixed in `scripts/p2_run.py` (2026-11-28): the three deletions are removed, so cem.yaml's values are merged onto plan_wall.yaml's planner block as the official sweep does, and `r3 cem` runs CEM alone and writes `results/p2_r3_cem.md`. The fix is untested: Hydra can't run on the laptop. **Plain CEM: planned; not run due to this week's GPU budget** (decided 2026-11-28; estimate 3.5–4 GPU-h at ~7 min per optimisation step).
- Prediction error vs. horizon (P2-R4, approved 2026-11-28, cap 30 GPU-min): official checkpoint, open loop with the real actions, decoder off, on the official validation split (192 trajectories). Error is the MSE of the visual patch features and of the proprio embedding, as the official training losses define them, plus a "nothing moves" baseline. Requested horizons were 1, 5, 10 and 20 steps. Each model step is 5 simulator steps, and the Wall data has 50 actions and states per trajectory (P2-R0), so the official data gives frames 0, 5, ..., 45, i.e. at most **9 model steps (45 simulator steps)**. We report every horizon from 1 to 9 model steps. That covers 1, 5 and 20 simulator steps (= 4 model steps) but not 10 or 20 model steps.
- Planning-budget study (MPC iterations vs. success) dropped (decided 2026-11-28): too expensive at ~75 min per MPC iteration on a T4.
